# 业务文档生成器

代码是真相源，文档是它的投影。本 skill 把文档生成拆成四个正交参数（类型 / 范围 / 受众 / 叙事）和一条证据链，使同一份代码可以稳定产出面向不同读者的不同文档，而不是靠提示词临时约定。

**工作角色**：技术专家。交互语言保持技术精确；输出文档的语言、深度、问题口径由受众参数决定，章节顺序与聚合方式由叙事参数决定。

---

## 结构地图

| 文件 | 作用 | 何时读 |
|---|---|---|
| `references/composition-matrix.md` | 类型 × 范围 → 章节集合；`narrative` → 顺序与聚合。**唯一的章节依据** | 确定参数后，生成骨架前 |
| `references/audience-profiles.md` | 受众 → 术语/证据/问题口径/深度。**唯一的渲染依据** | 生成骨架前 |
| `references/evidence.md` | 三级标注、锚点格式、密度规则。**唯一的证据依据** | 写第一条标注前 |
| `references/types/<type>.md` | 单类型的 base 章节与写作要点 | 生成该类型时 |
| `references/exploration-strategy.md` | 读哪些文件、怎么提取 | 第一轮扫描时 |
| `references/reverse-sync.md` | 模式 B 的五步规程 | 仅反向同步模式 |
| `dimensions/operations-manual.md` | 运营手册的七个分析维度 | 仅运营手册 / 管理员速查 |
| `scripts/validate_doc.py` | 结构、证据、脱敏、一致性校验 | 每次收尾必跑 |

**渐进加载**：先读本文件；只在需要时读上表对应的 2–3 个文件，不要一次全读。

## 第零步：模式判定

**A. 生成模式**：文档不存在，或需要按参数重新生成。
**B. 反向同步模式**：文档已存在且可能漂移，以代码为准校准。

命中「更新文档 / 同步文档 / 文档漂移 / 文档和代码对不上 / 反向同步」→ 模式 B，转 `references/reverse-sync.md`，**停止阅读本文件的四轮流程**。

其余 → 模式 A，继续。

---

## 第一步：参数确认（模式 A）

### 必问（硬阻断，未确认不得读代码）

1. **类型**（11 选 1）
2. **范围**（4 选 1）

```
立项   brd-mrd      商业/市场需求
需求   prd          产品需求
架构   hld          概要设计
架构   ddd          领域设计
实现   lld          详细设计
实现   coding-guide 编码指南
验证   test-doc     测试文档（可指定 bdd / sit / e2e / uat 变体）
运维   operations-manual  运营手册
运维   slo          SLI/SLO 与可观测性
发布   cicd         流水线文档
管理   admin-quick-reference 管理员速查

范围：
  module     单模块：一个模块的完整实现，读者能接手开发
  subsystem  子系统：多模块协同 + 部署单元 + 集成边界
  project    项目级：整个系统交付，含业务背景、非功能、验收、运维
  package    交付包：多份文档 + 1 份索引
```

若用户只说了「详细设计」这类类型词而未说范围 → **必须问范围**，不得默认。

### 可推断但必须声明（不阻断）

- **受众**：按 `audience-profiles.md` 的类型默认值推断，在参数卡中显式写出。
- **叙事**：按受众推断——`business` → `review`，其余 → `engineering`。取值见 `composition-matrix.md` 第六节。用户指定时以用户为准。
- **落点**：
  - 默认 `docs/<项目名>/<文档全称>-<系统名>.md`
  - 当范围或受众偏离该类型默认值时，追加 `-<scope>-<audience>`
  - 目标文件已存在 → 强制三选一：**覆盖 / 新建带版本号 / 合并**

### 输出参数卡（生成任何内容之前）

```
参数卡
- 类型：lld（详细设计）
- 范围：project（项目级）
- 受众：business（业务/验收方）  ← 默认值已声明
- 叙事：review（业务主线 + 技术保障）  ← 按受众推断
- 落点：docs/tender-demo/详细设计-tender-service-project-business.md
- 代码基线：<commit 或 快照哈希>
```

参数卡输出后即可继续；用户未反对即视为接受默认值。

**优先级**：用户显式给出的章节列表 > 参数卡 > 内置默认值。

## 第二步：四轮工作流

每轮的**产出物**固定，**读什么**由类型决定。

### 第一轮：项目识别与基线

- 读根目录（不递归），识别项目类型：`package.json` / `pom.xml` / `go.mod` / `Cargo.toml` / `*.csproj` / `requirements.txt` / `*.xcodeproj` / `AndroidManifest.xml` / `pubspec.yaml` / `CMakeLists.txt` / `*.sln`
- 找入口：`main.*` / `Application.*` / `Program.*` / `index.*`
- 读现有文档：`README.md`、`docs/`、`wiki/`
- **记录基线**：Git 仓库取 `git rev-parse --short HEAD` + 分支；非 Git 取关键文件哈希或日期快照
- 产出：项目类型、技术栈与版本、模块清单、基线

### 第二轮：结构扫描

按 `references/exploration-strategy.md` 的高信息密度位置读取。至少覆盖：

- 接口/路由注册（功能清单骨架）
- 数据模型与 DDL
- 业务逻辑层（规则、状态机、公式）
- 配置与默认值
- 错误码/异常处理
- 测试文件（现有覆盖）
- 构建与部署配置

大仓库（>50 文件）先用脚本提取清单，再定点精读，不逐行通读。

### 第三轮：逐模块分析

按类型的分析维度展开：

| 类型 | 分析重点 |
|---|---|
| brd-mrd | 业务问题、能力边界、价值产出、未覆盖场景 |
| prd | 用户故事、验收条件、业务规则、约束 |
| hld | 模块职责、依赖、关键决策与 trade-off、数据流 |
| ddd | 聚合、不变量、领域事件、上下文边界 |
| lld | 接口签名、数据结构、流程与异常路径、并发与事务、性能边界 |
| coding-guide | 实现模式（正例/反例/原因）、约定、陷阱 |
| test-doc | 输入输出边界、状态转换、异常场景、现有覆盖缺口 |
| operations-manual | 七维度（见 `dimensions/operations-manual.md`） |
| slo | 指标来源、超时配置、错误率、依赖拓扑 |
| cicd | 流水线阶段、触发条件、环境矩阵、回滚 |
| admin-quick-reference | 管理域划分、权限、危险操作、影响链 |

规则：
- 看不懂的逻辑先找调用方，再找测试，最后才读实现
- 枚举找定义处 + 使用处
- 无法确定标 `〔INFER〕`，不猜
- 每模块分析完立即整理，不攒到最后

### 第四轮：两阶段生成

**Step 1 骨架**
读 `composition-matrix.md` + 类型文件，得到章节集合；再按参数卡中的 `narrative` 取第六节的变体，得到章节顺序与聚合方式。只输出标题与一句话说明，不填内容。
- 若 `narrative=review`，骨架必须标出"业务主线 / 技术保障 / 附录"三段归属，并标明第 9、10 章的压缩上限。
- 交互模式：输出骨架后等待确认
- 自动模式（用户明确要求一次完成）：跳过确认，直接 Step 2，但收尾必须报告"骨架未经人工确认"

**Step 2 填充**
逐章填充；每章按类型文件的写作要点 + 受众档位渲染。
所有推断内容按 `evidence.md` 标注。

## 第三步：收尾（三项，逐项执行）

### 1. 机器校验（必须通过才能汇报）

```bash
python3 scripts/validate_doc.py <文档路径> \
  --root <项目根> --profile <类型> --audience <受众>
```

- `missing`（文件不存在、行号越界、符号找不到）→ **必须修复**
- `unverifiable`（非 Git、生成代码、动态语言定位不到）→ 记录并继续
- 敏感信息命中 → **必须修复**
- 结构错误（表格列数、围栏、Mermaid）→ **必须修复**
- `package` 模式：确认 `00-口径对照.md` 存在，且「冲突项」为空；否则交付包不完整

### 2. 文档同步铁律

以本次涉及的模块名为关键词搜索 `docs/<项目名>/`：

| 结论 | 动作 |
|---|---|
| 一致 | 跳过，记录原因 |
| 落后 | 立即更新 |
| 实现偏离设计意图 | 告知用户请求裁决，用 `〔OBSERVE｜缺陷｜…〕` 记录，不静默改写 |

禁止输出「文档待后续更新」。

### 3. 汇报（四项必答）

- 覆盖了哪些模块、哪些没覆盖、为什么、可能漏什么
- `INFER` 清单及推断依据
- 校验结果：错误数、警告数、`unverifiable` 数
- 偏离项与待裁决项

---

## 硬规则

1. **证据**：事实用 `〔FACT｜路径#符号:行号｜基线〕`，推断用 `〔INFER〕`，问题用 `〔OBSERVE｜类型｜严重度｜状态〕`。格式只在 `evidence.md` 定义。
2. **脱敏**：不出现真实密钥、口令、Token、内网完整地址、个人手机号。配置写占位符。
3. **单一事实源**：术语表、标注规范、章节模板各只在一处定义；其他文件引用，不复制。
4. **不写「待定」**：不确定项三选一——一致 / 立即更新 / 升级裁决。
5. **不设凑数指标**：章节内的"已知局限""建议"等，有则写、无则省略，只设上限不设下限。
6. **受众不改章节**：受众只改变写法与深度，不得删减 base 章节；确需删减必须由用户显式要求。
7. **范围决定扩展**：新增章节只能来自 `composition-matrix.md` 的扩展列，不得临场发明。
8. **叙事只改顺序**：`narrative` 决定章节顺序、聚合与压缩比例，不得删减章节主题，不得改变事实强度。跨受众交付必须走 `package` 模式并产出 `00-口径对照.md`。

## 示例：同一代码的两种参数卡

```
# 客户评审版
类型：lld  范围：project  受众：business  叙事：review
落点：docs/<项目>/详细设计-<系统>-project-business.md
骨架：业务主线（1-7 章）→ 技术保障（8-13 章）→ 附录（14 章）
约束：第 9、10 章合计 ≤15%；正文不引 E 编号；风险章附"上线前甲方准备清单"

# 内部评审版
类型：lld  范围：project  受众：dev  叙事：engineering
落点：docs/<项目>/详细设计-<系统>-project-dev.md
骨架：按实现路径，问题清单靠后
约束：待裁决项单列；正文 OBSERVE 回指 P 编号；重复表只定义一次
```
