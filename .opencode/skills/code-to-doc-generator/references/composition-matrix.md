# 章节组合矩阵

**唯一章节依据。** 文档的章节集合只由 `base(type) ∪ extend(type, scope)` 决定；`base` 定义在 `references/types/<type>.md`，`extend` 定义在本文件。章节的**顺序与聚合**由 `narrative` 决定（见第六节），但 `narrative` 不改变章节集合。

---

## 一、范围的判定标准

| scope | 判定 | 最低要求 | 典型读者问题 |
|---|---|---|---|
| `module` | 一个可独立理解的模块、服务或核心链路 | 能照着接手该模块开发 | 这个模块怎么实现？ |
| `subsystem` | 多个模块协同，含至少一个部署单元与外部集成边界 | 能完成联调与发布 | 这些模块怎么配合、怎么上线？ |
| `project` | 整个系统交付 | 能支撑评审、验收与运维交接 | 系统解决什么问题、怎么验收？ |
| `package` | 多份文档的合订交付 | 一份索引 + N 份分册 | 我应该读哪一份？ |

判定不清时按低一档处理，并在参数卡里写明理由；不要用 `project` 掩盖没想清楚的边界。

---

## 二、矩阵

| 类型 | `module` | `subsystem` 追加 | `project` 追加 |
|---|---|---|---|
| `brd-mrd` | 不适用，最低 `project` | — | 市场与竞品、投入产出测算、里程碑与假设 |
| `prd` | 不适用，最低 `subsystem` | 系统级约束、跨模块流程 | 验收标准汇总、埋点与指标、发布计划 |
| `hld` | 不适用，最低 `subsystem` | 部署拓扑、集成接口清单 | 容量与扩展性、可用性与容灾、演进路线 |
| `ddd` | 不适用，最低 `subsystem` | 上下文映射全景 | 领域事件流、模型演进与迁移 |
| `lld` | — | 部署与运维、测试要点 | 业务背景与目标、非功能指标、验收标准、风险与应对、附录 |
| `coding-guide` | — | — | 分支与发布策略、脚手架与模板 |
| `test-doc` | — | 环境与数据准备、自动化入口 | 验收标准映射、测试数据与账号管理、CI 门禁 |
| `operations-manual` | 不适用，最低 `project` | — | 权限矩阵、故障应急预案、术语表 |
| `slo` | — | 容量与依赖假设 | 错误预算政策、容量规划、成本 |
| `cicd` | — | 环境矩阵 | 制品与版本策略、安全与合规检查 |
| `admin-quick-reference` | 不适用，最低 `project` | — | 财务与计费细则、审计与合规、权限对比 |

**"追加"是并集**，不是替换：`project` 同时拥有 `subsystem` 的全部扩展节。

---

## 三、全局必备项（所有类型、所有范围）

无论参数如何，文档必须包含：

1. **文档头**：文档名、版本、日期、**代码基线**、技术栈、文档状态
2. **目录**：与 H2 标题一一对应
3. **范围声明**：本文覆盖什么、不覆盖什么

`project` 范围额外强制：**非功能指标、验收标准、风险清单、部署运维**四节，即使内容很少也必须成节并说明"当前未定义"。

---

## 四、`package` 模式

### 必备产物

`package` 模式固定产出 **1 份索引 + 1 份口径对照 + N 份分册**：

```
00-口径对照.md      ← 强制，缺此文件视为 package 未完成
README.md           ← 交付包索引
<分册 01..N>.md
```

### 索引

```markdown
# <项目名> 文档交付包

| 分册 | 类型 | 范围 | 受众 | 叙事 | 路径 | 状态 |
|---|---|---|---|---|---|---|
| 01 详细设计（评审版） | lld | project | business | review | ... | 已校验 |
| 02 详细设计（内部版） | lld | project | dev | engineering | ... | 已校验 |
| 03 测试文档 | test-doc | subsystem | dev | engineering | ... | 已校验 |

## 阅读路径
- 评审方：01 → 00 → 03
- 开发：02 → 00 → 03
- 运维：01 第 13 章 → 04
```

索引本身不写业务内容；每份分册独立校验。

### `00-口径对照.md`（强制）

跨受众的多份分册必然出现"同一事实、两种表述"。口径对照表的职责是证明**结论没有因为换受众而漂移**，不是复述内容。

```markdown
# 口径对照

基线：<commit / snapshot:YYYY-MM-DD>　对应分册：01、02

## 一、必须一致的结论

| 编号 | 结论（事实层） | 客户版表述 | 内部版表述 | 编号映射 | 一致性 |
|---|---|---|---|---|---|
| K-01 | 当前版本不具备生产发布条件 | 6 项上线前置条件未闭环，未闭环不得投入生产 | 发布准入：不可发布 | R-01→P0-02；R-02→P0-05；R-08→P0-05；R-09→P0-01；R-10→P0-04 | 一致 |
| K-02 | 目录生成链路在当前打包方式下不可用 | 目录结构稳定性下降（R-10） | P0-04：行为声明文件缺失 | R-10 ↔ P0-04 | 表述不同，结论相同 |

## 二、风险 ↔ 问题映射

| 客户版 | 内部版 | 映射依据 |
|---|---|---|
| R-01 明文凭据 | P0-02 | 同一配置文件同一行 |
| R-09 构建未产出可执行包 | P0-01 | 同一 `<skip>true</skip>` |

## 三、仅单侧存在的条目

| 编号 | 所在分册 | 不映射的原因 |
|---|---|---|
| P2-11 命名异味 | 02 | 纯内部工程债，对客户无可感知影响，按"版本外"处理 |

## 四、冲突项

| 编号 | 冲突描述 | 处理 |
|---|---|---|
| — | 无 | — |
```

### 映射规则（硬约束）

1. **每个 P0 必须映射**到客户版的某条风险，或进入第三节标"版本外"并写明"客户不可感知"的理由。不得留空。
2. **客户版每条"上线阻断"风险必须映射**到内部版至少一个 P0 或 P1。
3. 映射允许多对多（一条风险可能对应多个 P0，反之亦然）。
4. `一致性` 列三态：`一致` / `表述不同，结论相同` / `冲突`。出现 `冲突` 时，**交付包不得发布**，必须回到分册修正。
5. 口径对照表只写结论与映射，不复制分册正文。任一结论若需展开，指向分册章节。

> 判定标准：把 00 单独交给第三方，应能在不看分册的情况下回答"这两份文件说的是同一件事吗"。

---

## 五、新增章节的规则

1. 新章节必须先进入本矩阵，再进入类型文件；顺序反了就会产生"只有某次生成才有"的孤儿章节。
2. 用户显式给出的章节列表优先于矩阵，但必须在参数卡中标注"用户自定义章节"，并在收尾汇报中说明偏离。
3. 同义章节只保留一个名字（如"非功能设计"与"非功能需求"择一），避免检索困难。

## 六、叙事变体（`narrative`）

### 6.1 三个取值

| narrative | 适用 | 组织原则 | 默认搭配受众 |
|---|---|---|---|
| `engineering` | 开发、架构、运维接手 | 按**实现路径**排：是什么 → 怎么搭 → 数据 → 接口 → 异常 → 问题 | `dev` / `architect` / `operator` |
| `review` | 业务评审、交付验收、投标应答 | 按**决策路径**排：为什么做 → 谁在什么环节做什么 → 怎么判合格 → 有什么前提 | `business` |
| `acceptance` | 验收测试、UAT、合同交付 | 按**判定项**排：每条 AC 独立成节，给验证方法、证据、不通过后果 | `business` / 验收方 |

判定不清时按受众默认：`business → review`，其余 → `engineering`。参数卡中必须显式写出 narrative，并注明"按受众推断"或"用户指定"。

### 6.2 三条不变量

1. **narrative 不改章节集合。** 同一 `type × scope` 下，`engineering` 与 `review` 覆盖的章节主题完全一致，下限相同。只允许合并、下沉、重排。
2. **narrative 不改事实强度。** 同一结论在两种叙事下措辞可以不同，判定必须相同；跨分册的一致性由 `package` 模式的 `00-口径对照.md` 强制。
3. **narrative 不改证据链。** 锚点语法、基线、密度规则仍以 `evidence.md` 为准，narrative 只决定证据放在正文还是附录。

### 6.3 `lld × project × narrative=review` 骨架

两段式加附录，共 14 章。第一部分面向评审席，第二部分面向技术评委，第三部分是复核附件。

| 部分 | 章 | 承载的矩阵章节 | 写法要求 |
|---|---|---|---|
| **一 业务主线** | 1 文档说明 | 全局必备项 | 给"按角色阅读路径"表，不给文件清单 |
| | 2 项目概述 | 模块概述 + 业务背景与目标 | 痛点表、目标表、角色表、典型场景 |
| | 3 端到端业务流程 | 核心流程（业务视角） | 角色 × 环节 × 系统反馈 × 输出物，一张主流程图 |
| | 4 功能详细设计 | 接口设计 + 核心流程（业务可见部分） | 逐功能写"入口 / 处理 / 规则 / 输出 / 异常提示"，末尾给业务规则表 |
| | 5 非功能与验收口径 | 非功能指标 + 性能与限制 | 每个指标三列：目标值 / 依据 / 验收判定（见 6.5） |
| | 6 测试与验收 | 验收标准 + 测试要点 | AC 编号可判定；已知边界确认项单列，不混入 AC 表 |
| | 7 风险与上线前置条件 | 风险与应对 | 每条含影响、措施、责任方、计划；末尾给"上线前甲方准备清单" |
| **二 技术保障** | 8 总体设计 | 模块概述（技术侧）+ 拓扑 | 逻辑架构、模块划分、部署拓扑、选型说明 |
| | 9 核心组件与协作 | 组件职责 | **压缩**，见 6.4 |
| | 10 关键机制 | 状态机 + 异常处理策略的机制部分 | **压缩**，见 6.4 |
| | 11 数据设计 | 数据结构 | 实体、关键字段、索引约束、ER 图；不逐字段抄 DDL |
| | 12 接口设计 | 接口设计 | 用途、参数、返回、失败提示、调用示例 |
| | 13 部署与运维 | 部署与运维 | 环境要求、步骤、配置项、健康检查、常见问题 |
| **三 附录** | 14 附录 | 附录 | 错误码/提示总表、配置项总表、术语索引、证据索引 |

若用户显式给出的章节列表与此不同，以用户列表为准，但**部分归属与压缩比例仍然生效**（第 9、10 章对应的章节同样受 6.4 约束）。

### 6.4 第 9、10 章压缩规则（review 专用）

> 即工程叙事中的「核心组件与协作」「关键机制」两章；在两段式骨架中下沉到第二部分，编号变为第 9、10 章。以下约束按位置生效，不按标题生效。

| 约束 | 数值 | 判定方式 |
|---|---|---|
| 两章合计占全文篇幅 | ≤ 15% | 两章字符数 ÷ 全文总字符数（无工具时按行数近似） |
| 单章占全文篇幅 | ≤ 8% | 同上 |
| 每个组件 | 只保留一行职责 + 一个失败模式 | 不写能力清单逐项展开 |
| 协作 | 只保留一张时序图 | 不按功能逐个画 |
| 机制 | 只保留状态机、降级矩阵、幂等结论 | 不写逐路径线程与阻塞分析 |

被压缩掉的技术细节**不删除事实**，改为：

- 需要开发执行的细节 → 下沉到第 11、12、13 章；
- 只对复核有用的细节 → 进附录，或提升为证据索引条目；
- 与客户承诺无关的实现选择 → 不写。

压缩后必须在第 9 章开头用一句话声明"本章为技术保障摘要，实现细节见第 11–13 章"，让技术评委知道去哪找。

### 6.5 review 的两条强约束

1. **未测量指标必须给验收后果。** 第 5 章不得出现孤立的"未测量"；每个未测量值后面必须跟"验收时实测；未达标按 AC-xx 判定不通过"。目标值无代码依据时标 `〔INFER〕` 并写推断依据。
2. **风险章必须汇总甲方动作。** 责任方为甲方或"双方"的条目，在第 7 章末尾汇总成"上线前甲方准备清单"表：事项 | 对应风险 | 完成判据 | 最晚时间。清单缺项视为 review 骨架未完成。

### 6.6 review 与 engineering 的差异对照

| 维度 | `engineering` | `review` |
|---|---|---|
| 首章 | 结论摘要 + 读者与用途 | 阅读路径 + 范围声明 |
| 问题位置 | 靠后（第 11 章） | 靠前（第 7 章） |
| 未测量指标 | 写"未测量"并给测量方式 | 写"验收时实测 + 未达标后果" |
| 组件与机制 | 完整展开 | 压缩至 ≤15%，细节下沉 |
| 附录证据索引 | 正文可引 `见 E-xx` | 正文不引 E 编号，只引章节 |
