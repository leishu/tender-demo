# 反向同步规程

**定位**：以代码与运行产物为真相源，校准已存在的描述性文档。
**触发**：更新文档 / 同步文档 / 文档漂移 / 文档和代码对不上 / 反向同步。

标注语法一律引用 `evidence.md`，本文件不重复定义。

---

## 一、核心概念

| 概念 | 定义 |
|---|---|
| PRACTICE | 可被外部验证的成果：源码、配置、DDL、运行结果、交付物 |
| DESCRIPTION | 说明性文本：PRD、设计文档、README、规范、决策记录 |
| 铁律 | 两者冲突时以 PRACTICE 为准；DESCRIPTION 服务于 PRACTICE |

文档腐烂不是态度问题，是缺少反馈回路：改代码会编译失败，改文档不会。反向同步就是用流程补上这个回路。

---

## 二、五步规程

### Step 0 勘测

1. 区分 PRACTICE 与 DESCRIPTION
2. 给 DESCRIPTION 打角色标签：需求 / 计划 / 架构 / 决策 / 规范 / 索引 / 经验 / 其他
3. 确认排除项（历史归档、研究资料）并说明理由
4. 产出：产物清单表（路径 | 类型 | 角色 | 是否纳入）

### Step 1 解析

产出两类记录：

- **FACTS**：实际行为、契约、依赖、边界，每条附锚点
- **OBSERVATIONS**：按四个视角扫描

| 视角 | 关注 | 标签 |
|---|---|---|
| 宏观-架构 | 循环依赖、层级穿透、不合理耦合 | 债务 / 缺陷 |
| 中观-路径 | 主链路、同步等待、N+1、串行锁 | 性能 / 风险 |
| 微观-语义 | 魔法数字、含糊命名、失效注释 | 异味 / 债务 |
| 纵深-隐患 | 全局状态、吞异常、竞态、资源泄漏 | 缺陷 / 风险 |

每条 OBSERVATION 含：类型、严重度、定位、现象、建议。无把握写"待裁决"。

### Step 2 差异对照

| 状态 | 含义 | 处理 |
|---|---|---|
| 一致 | 描述与实际相符 | 跳过，记录原因 |
| 漂移 | 描述与实际不符 | 以 PRACTICE 为准更新 |
| 缺失 | 已落实但无描述 | 找归宿，补写 |
| 僵尸 | 描述了但未落实 | 标记移除候选，请用户确认 |

归宿路由：

| 内容 | 归宿 |
|---|---|
| 需求 / 规则 | 需求类文档 |
| 结构 / 依赖 | 架构类文档 |
| 决策 / 经验 | 决策类文档 |
| 入口 / 定位 | README 或索引 |
| 无归宿 | 进入待裁决 |

### Step 3 回写

- 保留原文档风格与结构，不重排、不改版式
- 新增内容按 `evidence.md` 标注
- 历史快照只在顶部追加"已被 X 取代"，正文不动
- 移除僵尸内容前必须确认

### Step 4 沉淀

- 在项目根维护 `OBSERVATIONS.md`（单仓库单文件；monorepo 放仓库根，不放子包）
- 按严重度分章，每条含类型、定位、扫描日期、处理状态
- 下次扫描先读本文件，跳过"已忽略"
- 不主动生成决策条目；发现"有意为之的反直觉设计"时列入"疑似决策点"，交人判断

### Step 5 去水

- 删除低信息密度段落、模糊修饰、过时描述
- 每段保留内容须对应至少一条 FACT 或一条决策依据
- 检查入口文档是否反映结构性变更

---

## 三、收尾六项（逐项回答，不可跳过）

```
① 产物清单已确认，扫描范围与排除项已声明
② 差异已三选一处理，无"待定"
③ OBSERVATIONS 已沉淀，含严重度与状态
④ 经验自问：再做一次希望提前知道什么？无则写"本次无新洞察"
⑤ 待裁决项已汇总
⑥ 入口文档已检查
```

> "偏离"最容易被误判为"落后"。开发者常把"我改得更好"当作"原计划如此"，静默把文档改成与新实现一致，丢失"这里发生过设计变更"的信息。偏离点应写入决策记录，而不是覆盖旧描述。

---

## 四、红线

1. 只读 PRACTICE，禁止修改代码、配置、设计稿
2. 沿用既有文档结构与命名，不臆造新文件
3. 不写未落实的内容，不保留已被淘汰的描述
4. 所有推断按 `evidence.md` 标注
5. 禁止"待定"，必须三选一：一致 / 立即更新 / 升级裁决

---

## 五、与生成模式的衔接

反向同步完成后，若某类文档缺失且用户需要，转入模式 A 生成；参数卡中的基线沿用本次扫描的基线，避免两份文档锚点不一致。
