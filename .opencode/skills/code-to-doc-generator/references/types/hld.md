# 类型：HLD 概要设计（`hld`）

## 解决什么问题

让架构评审者理解系统由哪些部分组成、如何交互、为什么这样选。回答"是什么、为什么"，不回答"怎么实现"。

## 默认参数

| scope 默认 | 受众默认 | 落点后缀 |
|---|---|---|
| `subsystem` | `architect` | 无 |

`module` 不适用，最低 `subsystem`。

## base 章节

1. 系统概述与上下文（C4-style 上下文图）
2. 架构总览（风格、分层图、主链路时序）
3. 模块划分（职责、对外契约、依赖、约束）
4. 数据模型概览（ER 图 + 关键字段，非全量）
5. 关键设计决策（ADR）
6. 跨切面关注点（认证、错误处理、日志、配置）

`project` 追加：容量与扩展性、可用性与容灾、演进路线。

## 各章要点

**上下文图**：外部系统 ↔ 本系统 ↔ 存储，标出协议与方向。

**模块划分**：每模块 1–3 句职责；对外接口只写输入输出，不展开实现；列出依赖与被依赖。

**ADR**：至少 3 条。每条含背景、选项对比表（方案 | 优点 | 缺点）、采用方案与理由、后果（trade-off）。没有 trade-off 的决策不是决策。

**跨切面**：认证授权、错误处理、可观测性、配置管理，四项各一小节。

## 写作规范

- 图优先，文字补充
- 不写类名与方法名，除非是架构级组件
- 决策必须给理由与代价，禁止"选用了 X 方案"就结束

## 常见失败

| 失败 | 纠正 |
|---|---|
| 写成模块清单 | 补交互图与决策 |
| 决策无 trade-off | 补选项对比与代价 |
| 下沉到实现细节 | 移到 `lld` |
| 只有 happy path 架构 | 补失败与降级路径 |

## 边界

- 领域模型与聚合 → `ddd`
- 接口参数与错误码 → `lld`
- 容量数字的测量细节 → `lld` 或 `slo`
