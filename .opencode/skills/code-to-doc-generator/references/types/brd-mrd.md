# 类型：BRD / MRD 商业需求（`brd-mrd`）

## 解决什么问题

让决策层判断"这件事值不值得做、边界在哪、成功怎么衡量"。不解释实现。

## 默认参数

| scope 默认 | 受众默认 | 落点后缀 |
|---|---|---|
| `project` | `business` | 无 |

`module` / `subsystem` 不适用，最低 `project`。

## base 章节

1. 背景与机会（痛点、市场、用户群体）
2. 产品目标与成功指标
3. 范围边界（在范围内 / 不在范围内）
4. 干系人分析
5. 风险与假设
6. 待裁决问题

`project` 追加：市场与竞品、投入产出测算、里程碑与假设。

## 各章要点

**痛点**：从代码、注释、README、现有流程推断，标 `〔INFER〕` 并给来源（"从认证模块的角色定义推断"）。

**成功指标**：可量化。禁止"提升效率""优化体验"，写成"人工操作从 X 步降到 Y 步"。

**范围边界**：不在范围内必须显式列出，并说明原因（技术限制、依赖未就绪、优先级）。

**干系人**：角色 | 核心诉求 | 影响方式。

**风险与假设**：假设逐条列出需要人确认的条目；风险给影响与缓解方向。

## 写作规范

- 全篇业务语言，不出现技术术语与代码结构
- 商业意图无法从代码验证，`〔INFER〕` 密度高于其他类型属正常
- 不给技术方案，只给目标与约束

## 常见失败

| 失败 | 纠正 |
|---|---|
| 把功能清单当商业价值 | 补"解决谁的什么问题" |
| 指标不可量化 | 改成数字与基线 |
| 假设未标注 | 逐条列 `〔INFER〕` |
| 越界给技术选型 | 移到 `hld` |

## 边界

- 功能细节 → `prd`
- 技术方案 → `hld`
- 验收 → `test-doc`
