# 类型：PRD 产品需求（`prd`）

## 解决什么问题

让产品、研发、验收方对"应该做什么、做到什么程度、怎么判定完成"达成一致。

## 默认参数

| scope 默认 | 受众默认 | 落点后缀 |
|---|---|---|
| `subsystem` | `business` | 无 |

`module` 不适用，最低 `subsystem`。

## base 章节

1. 背景与目标（问题、用户、价值）
2. 用户与场景（角色表、典型旅程）
3. 功能范围（全景图、在范围内 / 不在范围内）
4. 功能需求（逐功能）
5. 非功能需求
6. 待确认问题

`project` 追加：验收标准汇总、埋点与指标、发布计划。

## 各章要点

**功能需求**：每功能含用户故事（作为…我希望…以便…）、功能描述、业务规则、异常场景、验收标准。

业务规则用结构化条件：`当[条件]时，系统应[行为]`。

验收标准必须可判定：给定 / 当 / 则，或明确阈值。禁止"体验流畅""响应及时"。

**非功能**：性能、安全、兼容性，各给目标值与依据（代码现状 / 行业基线 / 产品要求）。

**待确认问题**：分析中发现的矛盾与模糊点，逐条给影响与建议。

## 写作规范

- 描述行为，不描述实现：写"每分钟最多 100 次"，不写 "rate limiter"
- 技术词首次出现给业务解释
- 从代码反推需求时，区分"已实现"与"设计意图"，后者标 `〔INFER〕`

## 常见失败

| 失败 | 纠正 |
|---|---|
| 把代码功能当需求 | 补"为什么需要" |
| 验收标准不可测 | 改为给定/当/则 |
| 遗漏不在范围内 | 显式写边界 |
| 无异常场景 | 每功能至少 2 条失败路径 |

## 边界

- 商业价值论证 → `brd-mrd`
- 接口与数据结构 → `lld`
- 测试用例 → `test-doc`
